= Protecting Passwords in WildFly
:summary: Protect passwords with Elytron credential stores and encrypted expressions, and use interactive tooling to avoid exposing secrets through management commands.
:includedir: /templates
include::../../templates/partials/guides/attributes.adoc[]
:wildfly-version: 42
:prerequisites-time: 30

The link:/guides/security-credential-store-for-passwords/[Using Credential Stores to Replace Clear Text Passwords, window=_blank] and link:/guides/security-credential-store-enc-exp/[Using Credential Stores With Encrypted Expressions, window=_blank] guides explain how to use credential stores and encrypted expressions in WildFly.

This guide complements them by bringing all the mechanisms together in a practical, step-by-step journey toward more secure password configuration in WildFly. Each step builds on the previous one, explaining the protection it provides and the remaining exposure we will address next.

We will begin by configuring an H2 datasource with a clear-text password, then move that password into an Elytron credential store and protect the store's own password with an encrypted expression. Next, we will examine how passwords can still appear in CLI history, management audit logs, and in-memory management operation history. Finally, we will provision credentials interactively with the Elytron Tool, avoiding clear-text passwords in management requests and command-line arguments.

[[prerequisites]]
== Prerequisites

* Roughly {prerequisites-time} minutes.
* JDK 25 with `JAVA_HOME` configured.
* A fresh https://www.wildfly.org/downloads/[WildFly 42.0.0.Final distribution, window=_blank], extracted locally. Set `WFLY_HOME` to its absolute path.
* A terminal with local access to the server's files. The examples use the Linux shell scripts supplied with WildFly.

The standard distribution includes the H2 JDBC driver.

For background, see link:/guides/security-credential-store-for-passwords/[Using Credential Stores to Replace Clear Text Passwords, window=_blank] and link:/guides/security-credential-store-enc-exp/[Using Credential Stores With Encrypted Expressions, window=_blank].

== Configure a datasource with a clear-text password

Start WildFly in one terminal:

[source,bash]
----
"$WFLY_HOME/bin/standalone.sh"
----

Connect to its management CLI in another terminal:

[source,bash]
----
"$WFLY_HOME/bin/jboss-cli.sh" --connect
----

In the JBoss CLI session, create our datasource using the following management operations:

[source, text]
----
/subsystem=datasources/data-source=SecureExampleDS:add(jndi-name=java:jboss/datasources/SecureExampleDS,driver-name=h2,connection-url="jdbc:h2:file:${jboss.server.data.dir}/secure-example",user-name=demo,password=DatabasePassword)
/subsystem=datasources/data-source=SecureExampleDS:test-connection-in-pool
----

The connection test should return:

[source, text]
----
{
    "outcome" => "success",
    "result" => [true]
}
----

The first connection creates the H2 database with user name `demo` and password `DatabasePassword`. WildFly persists the datasource configuration in `$WFLY_HOME/standalone/configuration/standalone.xml`. Its security element contains:

[source,xml]
----
<security user-name="demo" password="DatabasePassword"/>
----

An authorized management user can also read the configured password:

[source, text]
----
/subsystem=datasources/data-source=SecureExampleDS:read-attribute(name=password)
----

At this point, an authorized management user is anyone who can connect to the management realm via the CLI, the HTTP interface or JMX beans. You will probably want a more fine-grained configuration here. For example, you can configure user groups that have specific permissions over the server management model. To learn about how to do it, visit the link:https://docs.wildfly.org/{wildfly-version}/Admin_Guide.html#RBAC[Authorizing management actions with Role Based Access Control, window=_blank] section in the WildFly RBAC documentation.

In addition to RBAC, you would also configure the filesystem permissions where the server is running so that only the server process and authorized administrators can read the server configuration file.

That could be enough for you, but sometimes it is not, and you want to achieve additional protection for those sensitive passwords in case your configuration file is compromised.

Let's start by moving the passwords out of the server configuration file into a credential store.

== Move the password into a credential store

A credential store holds credentials under aliases. A resource with a `credential-reference` attribute can reference the store and use an alias instead of embedding the password.

Create a credential store and add the database credential and its alias:

[source,text]
----
/subsystem=elytron/credential-store=application-credentials:add(path=application-credentials.cs,relative-to=jboss.server.config.dir,credential-reference={clear-text=CStorePassword},create=true)
/subsystem=elytron/credential-store=application-credentials:add-alias(alias=db-password,secret-value=DatabasePassword)
----

The first management operation creates a credential store protected with the password `CStorePassword`. The second operation adds an alias named `db-password` that contains the existing H2 password and persists it in the `application-credentials.cs` store as a file under the server configuration directory.

Replace the datasource password with a reference to an alias using a batch, then reload:

[source,text]
----
batch
/subsystem=datasources/data-source=SecureExampleDS:undefine-attribute(name=password)
/subsystem=datasources/data-source=SecureExampleDS:write-attribute(name=credential-reference,value={store=application-credentials,alias=db-password})
run-batch
reload
/subsystem=datasources/data-source=SecureExampleDS:test-connection-in-pool
----

The configuration file for the datasource now contains:

[source,xml]
----
<security user-name="demo">
    <credential-reference store="application-credentials" alias="db-password"/>
</security>
----

The datasource password has been moved out of the server configuration file and now is stored in `application-credentials.cs`. Another advantage of using credential stores is that now we have the ability to modify our database password without having to modify the server configuration file, by simply updating the alias in the credential store.

However, the credential store itself requires a password in the configuration file:

[source,xml]
----
<credential-stores>
    <credential-store name="application-credentials" relative-to="jboss.server.config.dir" path="application-credentials.cs" create="true">
        <credential-reference clear-text="CStorePassword"/>
    </credential-store>
</credential-stores>
----

Anyone who can read the store file and obtain that password can recover the stored credentials. It is worth noting here how important it is that you protect the store file and the configuration file with the correct filesystem permissions, so that only the server process and authorized administrators can read them.

OK, we have removed the database password from `standalone.xml`, but the store password is still there in clear text. How can we protect that password too?

== Protect the credential-store password with an encrypted expression

WildFly must obtain the store password at startup to unlock the credential store. An encrypted expression lets us keep an encrypted value in the configuration and have WildFly decrypt it at runtime.

First, create a separate store containing an AES key and configure an expression resolver that uses it. Run these operations in the management CLI:

[source,text]
----
/subsystem=elytron/secret-key-credential-store=application-secret-keys:add(path=application-secret-keys.cs,relative-to=jboss.server.config.dir)
/subsystem=elytron/expression=encryption:add(resolvers=[{name=app-resolver,credential-store=application-secret-keys,secret-key=key}])
----

By default, the `secret-key-credential-store` resource creates its file and generates a 256-bit AES key under the alias `key`. The resolver named `app-resolver` is now configured to use that key to encrypt and decrypt expressions.

A `secret-key-credential-store` uses a `PropertiesCredentialStore` to store secret keys, not password credentials. Its contents are not encrypted or password-protected. The generated key is stored in the `application-secret-keys.cs` file, at this moment under the server configuration directory. Restrict access to the key file to the server's operating-system user and authorized administrators. Anyone who can read the key file can decrypt the store password and recover the database password.

Now we can ask the server to encrypt the password of our credential store:

[source,text]
----
/subsystem=elytron/expression=encryption:create-expression(resolver=app-resolver,clear-text=CStorePassword)
----

The result contains an `expression` value in this form:

[source,text]
----
{
    "outcome" => "success",
    "result" => {"expression" => "${ENC::app-resolver:YOUR_TOKEN}"}
}
----

Replace `YOUR_TOKEN` below with the token returned by your server, keeping the surrounding `${ENC::app-resolver:...}` expression. Update the existing credential store, reload, and test the connection:

[source,text]
----
/subsystem=elytron/credential-store=application-credentials:write-attribute(name=credential-reference,value={clear-text="${ENC::app-resolver:YOUR_TOKEN}"})
reload
/subsystem=datasources/data-source=SecureExampleDS:test-connection-in-pool
----

The test connection should succeed. This changes how WildFly obtains `CStorePassword`; it does not change the store's password or its aliases.

The Elytron credential-store configuration now contains:

[source,xml]
----
<credential-stores>
    <credential-store name="application-credentials" relative-to="jboss.server.config.dir" path="application-credentials.cs" create="true">
        <credential-reference clear-text="${ENC::app-resolver:YOUR_TOKEN}"/>
    </credential-store>
    <secret-key-credential-store name="application-secret-keys" relative-to="jboss.server.config.dir" path="application-secret-keys.cs"/>
</credential-stores>

----

Although the attribute is named `clear-text`, its value here is an encrypted expression. WildFly resolves it at runtime to unlock the store, then retrieves the database password through the datasource's `db-password` alias.

You can use encrypted expressions not only for the credential-reference clear-text attribute, but also on any management attribute that supports expressions. For example, you could use an encrypted expression to protect the database password directly in the datasource configuration, without using a credential store. However, that would require updating the datasource configuration whenever the password changes. Using a credential store allows you to update the password under the same alias without changing the server configuration file. Credential stores can also be reloaded at runtime, so depending on the resource, you may not even need to restart or reload the server to use the updated password.

Neither password now appears in clear text in the current server configuration. OK, so far so good. However, we entered both passwords through management operations. Where might those original values have been recorded?

== Where passwords can still be recorded

=== Configuration history files

WildFly automatically maintains https://docs.wildfly.org/{wildfly-version}/Admin_Guide.html#Configuration_file_history[configuration file history, window=_blank] as part of persisting the server configuration. Before a management operation's changes are written to the configuration file, WildFly saves a copy of the previous XML configuration. This is built-in behavior and does not require enabling a history service. For the standalone server used in this guide, these files are stored under `$WFLY_HOME/standalone/configuration/standalone_xml_history`.

Earlier configuration copies can still contain `DatabasePassword` and `CStorePassword` in clear text. Replacing passwords with credential references or encrypted expressions updates the current configuration; it does not remove those values from existing history files, snapshots, or external backups. Configuration history persists across server restarts.

Restrict access to these files to the server process and authorized administrators, and review retained copies containing clear-text passwords according to your backup and retention requirements.

=== Local CLI history

Run `history` in the management CLI. Depending on your CLI history configuration, the earlier commands containing `DatabasePassword` and `CStorePassword` will appear. By default, the CLI also persists history in `.jboss-cli-history` in the user's home directory; its location is configurable.

For commands that contain sensitive values, you should disable history *before* entering the command:

[source]
----
history --disable
----

After completing the sensitive operations, restore history with:

[source]
----
history --enable
----

Disabling history affects subsequent input in that CLI session. It does not erase existing entries or hide commands already displayed in a terminal.

=== In-memory management operation history

The `core-management` subsystem provides an optional https://docs.wildfly.org/{wildfly-version}/Admin_Guide.html#configuration-changes[in-memory configuration-change history, window=_blank] that retains recent management operations. This service is separate from the automatic XML configuration file history and is disabled by default. For example, `/subsystem=core-management/service=configuration-changes:add(max-history=10)` enables it with a limit of ten entries, independently of the client's local history setting.

This history can contain sensitive operation parameters, including passwords submitted through the operations described above. The history stored in memory is not persisted to disk and will be lost when the server is stopped. However, it can be read by an authorized management user while the server is running.

If it is enabled, you should disable the configuration-change history *before* entering sensitive management operations.

=== Management audit records

https://docs.wildfly.org/{wildfly-version}/Admin_Guide.html#Audit_logging[Management audit logging, window=_blank] records management requests when enabled. These records can contain sensitive operation parameters, independently of the client's local history setting. Disabling audit logging does not disable the separate in-memory configuration-change history.

For example, our `add-alias` operation submitted `DatabasePassword` as `secret-value`, and `create-expression` submitted `CStorePassword` as `clear-text`. The resulting credential reference or encrypted expression does not change what was submitted in those requests.

If it is enabled, you should disable management audit logging *before* entering sensitive management operations.

=== Shell history and process arguments

Running `jboss-cli.sh --command=...` from a shell adds another place where a command containing a password can be recorded: shell history and process arguments. It is worth mentioning that it doesn't bypass management audit logging or in-memory configuration-change history on the server.

OK, we can adjust these settings and disable the optional histories or logging before performing any sensitive operation. However, disabling management audit logging may not be a great idea, since we would want to continue recording any management change. We might not even be allowed to disable it.

So the question is, if we are not allowed to disable the management audit logging, and we want to avoid exposing passwords, what can we do?

[[interactive-provisioning]]
== Provision credentials interactively with the Elytron Tool

The Elytron Tool, available at `$WFLY_HOME/bin/elytron-tool.sh`, can create and manage credential stores locally. It prompts for passwords and secrets interactively, so those values are not exposed in shell-command arguments or management requests.

We could use this tool to create the credential store to store the alias and the secret-key-credential-store to create an encrypted expression to encrypt the credential store password.

=== Create and populate the credential store

Quit the interactive JBoss CLI session and create a credential store named `protected-credentials.cs` to store the alias we want to use to retrieve the database password:

[source,bash]
----
"$WFLY_HOME/bin/elytron-tool.sh" credential-store \
  --create \
  --location="$WFLY_HOME/standalone/configuration/protected-credentials.cs"
----

NOTE: In this example, we are creating a new credential store and saving it in the server configuration directory. Pay attention to the filesystem permissions of the store file, so that only the server process and authorized administrators can read it.

The tool prompts for the new credential-store password and confirmation. Choose a new store password, and retain it for the encryption step below. Input is not echoed when run in an interactive terminal.

Add the database credential under the alias `db-password`:

[source,bash]
----
"$WFLY_HOME/bin/elytron-tool.sh" credential-store \
  --location="$WFLY_HOME/standalone/configuration/protected-credentials.cs" \
  --add=db-password
----

The tool will ask you for:

. The credential-store password you created with the first command.
. The secret value for the alias and confirmation. Use the existing H2 password: `DatabasePassword`.

The store protects the database password under the alias `db-password`.

=== Generate a new expression resolver and encrypt the credential store password

WildFly still needs to unlock the new store at startup. This time, we will generate the AES key and encrypt the store password locally, without sending the password to the server's `create-expression` operation.

While the server is stopped, create a new `PropertiesCredentialStore` for the bootstrap key:

[source,bash]
----
"$WFLY_HOME/bin/elytron-tool.sh" credential-store \
  --create \
  --type=PropertiesCredentialStore \
  --location="$WFLY_HOME/standalone/configuration/bootstrap-keys.cs" \
  --generate-secret-key=key
----

NOTE: Ensure that the new property credential store has restrictive filesystem permissions, so that only the server process and authorized administrators can read it.

This generates a 256-bit AES key under the alias `key`. It does not print the key or require a store password. As with `application-secret-keys.cs`, the key file itself is not encrypted; the restrictive filesystem permissions protect it.

Use that key to encrypt the password you chose for `protected-credentials.cs`:

[source,bash]
----
"$WFLY_HOME/bin/elytron-tool.sh" credential-store \
  --type=PropertiesCredentialStore \
  --location="$WFLY_HOME/standalone/configuration/bootstrap-keys.cs" \
  --encrypt=key
----

Enter the *new credential-store password* at both prompts. We omit `--clear-text` so the value is entered interactively.

The output includes an encrypted token:

[source,text]
----
Clear text encrypted to token 'YOUR_GENERATED_TOKEN' using alias 'key'.
----

Keep your generated token for the next step. Each encryption can produce a different token, even for the same password and key.

The resulting chain is:

[source,text]
----
AES key in bootstrap-keys.cs
  -> decrypts the encrypted store-password expression
  -> unlocks protected-credentials.cs
  -> retrieves db-password for the datasource
----

=== Configure WildFly to use the chain

Open a new JBoss CLI interactive session:

[source,bash]
----
"$WFLY_HOME/bin/jboss-cli.sh" --connect
----

Register the existing key store and add the `bootstrap` resolver to the encryption resource we configured earlier:

[source]
----
/subsystem=elytron/secret-key-credential-store=bootstrap-keys:add(path=bootstrap-keys.cs,relative-to=jboss.server.config.dir,create=false,populate=false)
/subsystem=elytron/expression=encryption:list-add(name=resolvers,value={name=bootstrap,credential-store=bootstrap-keys,secret-key=key})
reload
----

`create=false` and `populate=false` ensure that the server uses the key we generated with the Elytron Tool. Using `list-add` preserves the `app-resolver` resolver we added at the beginning, which the original store still needs until we remove it. Reload to activate the new resolver before using its encrypted expression.

Replace `YOUR_GENERATED_TOKEN` below with the token from the tool, keeping the surrounding `${ENC::bootstrap:...}` expression:

[source]
----
/subsystem=elytron/credential-store=protected-credentials:add(path=protected-credentials.cs,relative-to=jboss.server.config.dir,create=false,credential-reference={clear-text="${ENC::bootstrap:YOUR_GENERATED_TOKEN}"})
/subsystem=datasources/data-source=SecureExampleDS:write-attribute(name=credential-reference,value={store=protected-credentials,alias=db-password})
/subsystem=elytron/expression=encryption:list-remove(name=resolvers, value=app-resolver)
reload
/subsystem=datasources/data-source=SecureExampleDS:test-connection-in-pool
----

The datasource now references the locally provisioned credential store, and management operations that modified the server configuration will continue being published in the management audit log.

We should be able to verify the connection works using the original password. These registration operations contain no clear-text passwords: the store password appears only as an encrypted expression, and the datasource refers to its alias.

== Choosing credential references or encrypted expressions

Use a credential reference where the resource supports one: the password lives outside the XML, and its value can be updated under the same alias without changing that reference. Coordinate credential store updates with database-password changes and restart or reload the relevant services so they use the updated credentials.

Encrypted expressions are also useful for attributes that support expressions but have no `credential-reference`. Updating such a value requires generating a new encrypted expression and updating the configuration. In this guide, the two mechanisms work together: an encrypted expression unlocks a credential store, and a credential reference supplies the datasource password.

== Current limitation

The Elytron Tool needs to be used locally, so if you need to provision credentials on a remote server keeping management audit logs and you do not want to expose sensitive values in those management audit logs, you must copy the store files and encrypted expression to the remote server. The Elytron Tool does not support remote management operations.

== What's next?

=== Redacting sensitive management-operation parameters

https://redhat.atlassian.net/browse/WFCORE-7247[WFCORE-7247, window=_blank] tracks the concern that sensitive management parameters can appear in audit logs and in-memory management operation history. Once this feature is implemented, sensitive parameters could be flagged for redaction, preventing them from appearing in those records and allowing the execution of those operations against a remote server without the need to populate the credential stores locally.

The planned filtering concerns server-side records. Precautions for history files and backups, local CLI history, and shell history still apply, and credential stores and encrypted expressions remain useful for protecting the persisted configuration.
